# Implementation Plan: viaim RecDot as a Native Omi Device

**Branch**: `feature/viaim-recdot-device` (TranscriptBoss) · `feature/viaim-recdot` (fork) · **Date**: 2026-09-06 · **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/002-viaim-recdot-device/spec.md`, protocol facts from [protocol.md](./protocol.md), decisions from [research.md](./research.md)

---

## Summary

Make the viaim RecDot a first-class Omi device: it appears in the device list, connects like an
Omi pendant, streams both sides of a phone call as two attributed channels into whichever
transcription mode the user already has (on-device by default), and syncs recordings made
without the phone into conversations, deleting them from the buds only once they are safe.

The shape is Omi's own: one `DeviceType`, one `DeviceConnection`, one `DeviceTransport` per
platform, and `AudioSource`s feeding the existing pipeline. The three things Omi lacks are
supplied as small, hermetically tested pure-Dart pieces: the buds' framing codec, a G.722
decoder, and a two-channel capture session that runs two on-device recognisers and merges by
time. Stored recordings reuse feature 001's import job after decode.

---

## Technical Context

**Language/Version**: Dart 3 / Flutter as pinned by the fork; Swift 5 for the iOS transport; Kotlin for the Android transport
**Primary Dependencies**: None added to `pubspec.yaml`. Pigeon (already Omi's bridge), ExternalAccessory.framework (iOS system), `BluetoothSocket` (Android system). A pure-Dart G.722 decoder ported from public-domain C
**Storage**: Omi's existing device store and WAL/import stores; per-transfer scratch files for decoded PCM, deleted on completion
**Testing**: `flutter_test` hermetic unit tests against JSON golden vectors generated by `scripts/recdot_wire.py` and the bit-exact Python G.722 package; Omi's `app/test.sh` gate; hardware evidence from the user's iPhone via TestFlight only
**Target Platform**: iOS first (iPhone, TestFlight); Android for parity, unverified on hardware
**Project Type**: Mobile — a change to the forked Flutter application, built to Omi's contribution standard
**Performance Goals**: Two-channel 16 kHz capture with two concurrent on-device recognisers for a one-hour call without dropped frames or thermal throttling; a one-hour stored recording imported within fifteen minutes of idle connection
**Constraints**: Never touches the call's own audio path; never transfers during a call or live capture; never deletes on the bud before durable persistence; no behaviour change to any existing device; no audio leaves the phone in on-device mode; no new dependency
**Scale/Scope**: One user, ~20 h/week, one phone; ~2,500 lines of Dart, ~400 Swift, ~300 Kotlin, plus tests

## Design (from research)

| Decision | Summary |
|---|---|
| D-1 Transport | `RecDotLinkTransport` over Pigeon; iOS `EASession` on `com.vision.voyager`, Android RFCOMM. Native = byte pipe; framing in Dart |
| D-2 Attribution | `RecDotCaptureSession`: on-device mode runs two `PurePollingSocket`s (user / remote) merged by start time; cloud mode sends channel-tagged frames with `channels=2` via an extended `TranscriptSegmentSocketService.create` |
| D-3 G.722 | Pure-Dart decoder ported from public-domain `libg722`, bit-exact golden vectors |
| D-4 FlashRecord | List → download → decode → verify → 001 import job → delete on bud only after durable persist |
| D-5 Discovery | Accessory list (iOS) / bonded headsets (Android); no BLE scan required; identity by serial prefix |
| D-6 Call edges | Bud push `0x5013` primary, platform call observer fallback and end signal |
| D-7 Delivery | Fork branch → `personal/ci` → Codemagic `ios-personal-dogfood` → TestFlight; Android after; upstream after sign-off |

## Complexity Tracking

| Id | Custom piece | Why the framework does not cover it | Simpler alternative rejected because |
|---|---|---|---|
| C-1 | `StarotCodec` (framing, TLV, audio split) | Omi has no generic framed-serial codec; each device carries its own (`ring_protocol.dart`, Limitless protobuf) | Framing in native code would need two untested implementations |
| C-2 | `G722Decoder` in Dart | No platform or Flutter G.722 decoder; backend decode puts audio on the cloud path | FFI to C needs two native builds with no local toolchain |
| C-3 | `RecDotCaptureSession` two-recogniser mode with time-ordered merge | On-device providers are mono; the backend channel contract exists only for cloud mode | Mono mix with energy attribution misattributes overlap and degrades transcripts |
| C-4 | `RecDotFlashSync` state machine | Omi's flash drain feeds the cloud WAL path; the import job covers everything after decode but not the bud-side download/delete protocol | Reusing `FlashPageWalSync` would transcribe in the cloud |

Article V note (carried from 001): a mobile app has no Cypress surface and the accessory link
cannot be containerised; integration evidence is the TestFlight table in quickstart.md.
